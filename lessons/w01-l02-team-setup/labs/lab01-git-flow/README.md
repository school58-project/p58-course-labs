# Лабораторная 01. Git-процесс

Команда договорилась о правилах (см. лекцию 1): ветка на каждую задачу, сообщения коммитов
`<область>: что сделано`, шаблон PR и `AGENTS.md` в корне. Звучит просто, но через неделю все про них забудут.
Поэтому DevOps решил: пусть правила проверяет робот. Так появился маленький модуль `gitflow.py` для CI.

Модуль дописали до половины и бросили: что-то работает с ошибками, чего-то нет вовсе.
Твоя задача — довести его до ума. У каждой задачи свои тесты, так что сразу видно, что уже получилось.

## Как идёт работа

Тут важен не только код, но и весь путь до сдачи: так же ты потом будешь работать в проекте.
Идём по шагам и строго по порядку:

0. **Подготовка** — вход на учебный сервер и SSH-ключи (один раз).
1. **Клон** репы курса на сервер (один раз).
2. **Своя ветка** для лабораторной — `<ваш-ник>/lab01`.
3. **Решение задач** в `gitflow.py`.
4. **Самопроверка** `python check.py`.
5. **Коммиты и push** своей ветки в репу курса.
6. **Pull request** в репу курса — это и есть сдача.

В каждом шаге есть «Как проверить». Пока проверка не сошлась, дальше не идём: иначе ошибка всплывёт
через три шага, и искать её будет больнее.
Подробная инструкция с примерами того, что отвечает сервер, — [«Учебный сервер: вход с Windows»](../../../../docs/server-windows.md);
ссылки ниже ведут сразу в нужный раздел.

## Шаг 0. Подготовка: вход на сервер и SSH-ключ

> ⚠️ Сейчас будет душно, держись: ключи, пароли и много команд подряд. Зато делается один раз.

Логин, адрес сервера и временный пароль даёт преподаватель. Команды набираем в PowerShell (Windows):
`Win+X` → «Терминал». Вместо `<логин>` и `<адрес>` подставляй свои значения без угловых скобок.

**0.1. Первый вход и новый пароль** — [инструкция, раздел 1](../../../../docs/server-windows.md#1-первый-вход-и-смена-пароля).
`ssh <логин>@<адрес>` → `yes` → временный пароль → сервер попросит сменить пароль и отключит → войдите снова
с новым паролем. Пароль при вводе не видно совсем, даже звёздочек. Это нормально, просто печатай.

* Как проверить: в начале строки `<логин>@p58-course:~$`.

**0.2. SSH-ключ на своём компьютере и ключ на сервер** —
[раздел 2](../../../../docs/server-windows.md#2-создать-ssh-ключ-на-своём-компьютере) и [раздел 3](../../../../docs/server-windows.md#3-положить-ключ-на-сервер).
На своём компьютере (не на сервере) `ssh-keygen -t ed25519 -C "<логин>"`, затем одна длинная команда из раздела 3,
которая кладёт открытый ключ на сервер.

* Как проверить ([раздел 4](../../../../docs/server-windows.md#4-проверить-вход-без-пароля-и-сделать-короткое-имя)):
  `ssh <логин>@<адрес>` пускает **без пароля**. Если хочется меньше печатать, настрой короткое имя `ssh p58`.

**0.3. GitHub на сервере** — [раздел 5](../../../../docs/server-windows.md#5-подключить-github-на-сервере).
На сервере: `ssh-keygen -t ed25519 -C "<логин>@p58-course"` (на все вопросы Enter),
`chmod 600 ~/.ssh/id_ed25519` (на всякий случай), `cat ~/.ssh/id_ed25519.pub` → строку добавить на GitHub
(**Settings → SSH and GPG keys → New SSH key**). Потом `git config --global user.name` и `user.email`.

* Как проверить: `ssh -T git@github.com` отвечает `Hi <ваш-ник>! You've successfully authenticated...`.
  Если `Permission denied (publickey)` — ключ на GitHub ещё не добавлен или скопирован не целиком.

Застрял — смотри [частые проблемы](../../../../docs/server-windows.md#7-частые-проблемы) или иди к преподавателю. Пароли и закрытые ключи
(файлы без `.pub`) никому не показываем и в чат не пишем. Даже «просто глянуть».

## Шаг 1. Клон репы курса

Подробно — [раздел 6 инструкции, «Один раз»](../../../../docs/server-windows.md#6-сдача-домашки-своя-ветка-и-pull-request).
Все работают в **одной общей** репе курса, каждый в своей ветке. Преподаватель добавит тебя в репу:
на почту от GitHub придёт приглашение. Прими его, иначе `git push` не пройдёт.

1. На сервере склонируйте репу курса:

   ```bash
   cd ~
   git clone git@github.com:school58-project/p58-course-labs.git
   cd p58-course-labs
   ```

2. Окружение Python (один раз, около минуты):

   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   python -m pip install -r requirements.txt
   ```

* Как проверить: `git remote -v` показывает `origin  git@github.com:school58-project/p58-course-labs.git`;
  в начале строки `(.venv)`. После каждого нового входа на сервер: `cd ~/p58-course-labs && source .venv/bin/activate`.

## Шаг 2. Ветка для лабораторной

Ветка для сдачи называется `<ваш-ник>/lab01`, где ник — твой ник на GitHub (например `kotik58/lab01`).
Это правило сдачи курса. Не путай с правилами веток в проекте ниже, они другие.

```bash
git switch main
git pull origin main             # свежие материалы курса
git switch -c <ваш-ник>/lab01
cd lessons/w01-l02-team-setup/labs/lab01-git-flow
```

* Как проверить: `git branch` — звёздочка у `<ваш-ник>/lab01`.

Правила общей репы:

* в `main` не коммитим и не пушим. GitHub всё равно не даст: `main` защищена;
* чужие ветки не трогаем (не пушим в них, не удаляем);
* вышли новые материалы — обнови свою ветку: `git switch <ваш-ник>/lab01 && git pull origin main`
  (git сделает merge-коммит — это нормально, сообщение можно оставить как есть).

## Шаг 3. Реши задачи

> ⚠️ Дальше таблица, где важна каждая буква и каждый дефис. Читай примеры внимательно: тесты проверяют именно их.

| № | Функция в `gitflow.py` | Что сделать | Что проверить |
|---|---|---|---|
| 1 | `slugify` | Транслитерировать русский заголовок issue в латиницу для имени ветки. Сейчас буквы «ё», «й», «щ» теряются, а пробелы склеиваются неправильно. | `slugify("Поле 6×7: ход в столбец")` → `"pole-6-7-hod-v-stolbec"` |
| 2 | `branch_name` | Собрать имя ветки `<тип>/<номер>-<slug>`. Неизвестный тип — `ValueError`. | `branch_name(12, "Кнопка «Играть»")` → `"feature/12-knopka-igrat"` |
| 3 | `is_valid_branch` | Проверить имя ветки по правилам проекта. Сейчас функция пропускает ветку без номера. | `feature/12-board` — да, `feature/board`, `Feature/12-x`, `main` — нет |
| 4 | `commit_problems` | Вернуть список нарушений в сообщении коммита (пустой список — всё хорошо). | `"fix"` → есть нарушения; `"bot: кнопка Играть"` → `[]` |
| 5 | `parse_log` и `count_by_area` | Разобрать вывод `git log --oneline` и посчитать коммиты по областям. | 3 коммита `game`, 1 коммит `bot` в примере из тестов |
| 6 | `pr_problems` | Проверить описание PR: обязательные разделы и ссылка `Closes #N`. | Описание без раздела «Что сгенерировал агент» не проходит |
| 7* | `agents_md_problems` | Проверить `AGENTS.md`: обязательные разделы и отсутствие секретов. | Строка `BOT_TOKEN=123:ABC` — нарушение |

Порядок любой. Задача со звёздочкой посложнее, её можно оставить на десерт.

## Шаг 4. Самопроверка

Нужен Python 3.12 или новее и pytest (на сервере всё ставится в шаге 1).

```bash
python check.py        # таблица: какие задачи уже проходят
python check.py -v 3   # подробности по задаче 3
```

* Как проверить: в конце `Готово задач: 7 из 7` (или сколько успел, сдавать можно и частично).

Тесты в папке `tests/` не трогай. Подкрутить тест, чтобы позеленел, не выйдет: преподаватель проверяет работу своими тестами.

## Шаг 5. Коммиты и push

На каждую задачу отдельный коммит по правилам проекта (`область: что сделано`, см. ниже). Не один коммит «всё» в конце:

```bash
git add gitflow.py
git commit -m "ci: slugify — буквы ё, й, щ"
git push -u origin <ваш-ник>/lab01      # первый раз; дальше просто git push
```

* Как проверить: `git log --oneline` — по сообщениям понятно, что в каждом коммите;
  на странице репы курса на GitHub в списке веток (**branches**) есть `<ваш-ник>/lab01`.

## Шаг 6. Pull request — сдача

Подробно — [раздел 6 инструкции, «Каждая домашка», пункт 5](../../../../docs/server-windows.md#6-сдача-домашки-своя-ветка-и-pull-request).
Открой ссылку, которую напечатал `git push` (или нажми **Compare & pull request** на странице репы курса).
Сверху должно быть `base: main` ← `compare: <ваш-ник>/lab01`. Название PR, например, `lab01: <ваш-ник>`.
В описании три раздела: `## Что сделано`, `## Как проверить`, `## Что сгенерировал агент`. Жми **Create pull request**.

* Как проверить: PR виден во вкладке **Pull requests** репы курса. Что-то исправил — коммит и `git push`
  в ту же ветку, PR обновится сам. Один PR на лабораторную. В `main` его никто не вливает: это просто способ сдать работу.

## Правила проекта (для справки)

> ⚠️ Душная, но полезная шпаргалка. Тесты из шага 3 проверяют ровно эти правила.

* Типы веток: `feature`, `fix`, `docs`, `chore`. Имя: `тип/номер-slug`, slug — латиница в нижнем регистре,
  цифры и дефисы, без дефисов по краям и без двойных дефисов.
* Области коммитов: `bot`, `api`, `game`, `web`, `tests`, `docs`, `infra`, `ci`.
  Сообщение: `область: описание`, описание с маленькой буквы, без точки в конце,
  вся первая строка не длиннее 72 символов.
* Описание PR содержит разделы `## Что сделано`, `## Как проверить`, `## Что сгенерировал агент`
  и строку `Closes #<номер>`.
* `AGENTS.md` содержит разделы `## Стек`, `## Правила`, `## Как проверить` и не содержит секретов.

## Git-часть (сдаётся у экрана)

1. Покажи свой PR и `git log --oneline --graph`: по сообщениям должно быть понятно, что в каждом коммите.
2. Запусти `python check.py` на своём `gitflow.py` и покажи, что твои коммиты проходят `commit_problems`.
3. Расскажи, почему мы не пушим в `main` и как подтянуть в свою ветку новые материалы.

## Если используете агента

Можно. Но на сдаче объяснять каждую строку будешь ты, а не агент. Рабочая схема: сначала сам прочитай тест задачи,
потом дай агенту тест и правила проекта как контекст, а его ответ проверь на своих примерах.
