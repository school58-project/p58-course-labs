Как играют из Telegram

Пользовательтелефон
→
Боткнопка «Играть»
→
Mini Appстраница с canvas
→
FastAPIнаш сервер
  • Бот присылает сообщение с кнопкой. Нажатие открывает веб-страницу внутри Telegram.
  • Страница — обычные HTML, CSS и JavaScript. Рисует поле, отправляет ходы.
  • Сервер на Python проверяет каждый ход и рассылает новое состояние.
Кто прав в споре «был ли ход»? Всегда сервер. Клиент только показывает.
Mini App
Telegram открывает URL во встроенном WebView и передаёт странице initData — подписанные данные о пользователе. Подпись проверяем на сервере (неделя 3).
Почему логика на сервере
Код в браузере можно изменить. Если клиент сам решает, что ход разрешён, любой может «выиграть» из консоли. Сервер — источник истины.

Четыре идеи на выбор

«4 в ряд» и классика
Пошаговые игры на сетке: крестики-нолики 5×5, «4 в ряд», морской бой. Проще всего начать.
Змейка на двоих
Realtime: тики, коллизии, синхронизация. Сложнее, зато зрелищно.
Карты и кубики
Покер на фишки, d20 с ведущим. Честный рандом и скрытая информация.
Библиотека игр
Каталог мини-игр с общим рейтингом и лобби. Важна архитектура.
Одна подкоманда берёт простую игру 1, вторая — игру 2 позже. Платформа общая: вход, рейтинг, лобби.
Критерии выбора
Можно ли сделать MVP за 3 недели? Есть ли мультиплеер? Есть ли что проверять на сервере? Интересно ли играть с телефона?
Расширения в Т3
ИИ-ведущий для d20, конструктор LLM-чата, ИИ-соперник (минимакс), аналитика матчей.
Риски
Realtime сложнее пошагового. Скрытая информация (карты) требует аккуратного протокола: клиенту нельзя отправлять чужие карты.
Что не берём
Игры с реальными деньгами, сбор лишних личных данных, копирование чужих брендов.

Почему роли, а не «все делают всё»
Когда за спеку отвечают все, её не пишет никто. Роль — это ответственность: кто последним говорит «готово».

ИИ-агент — участник команды

  • Агент умеет писать код, тесты, конфиги и находить ошибки.
  • Но агент не знает ваш проект, пока вы ему не расскажете.
  • И агент ошибается уверенно: код выглядит правильным, но не работает.
Правило года: за каждую строку в PR отвечает человек, даже если её написал агент.
Как работаем
Правила и контекст в AGENTS.md. Spec-first: сначала спека, потом код. Ревью агентом и человеком. Измеряем: сколько PR агента приняли, сколько итераций ревью.
Чего агенту не даём
Секреты, токены ботов, SSH-ключи, пароли от VPS. Решения «мержить ли в main». Данные пользователей.

Проверка: зачем это всё

Игрок прислал ход «поставить фишку в столбец 9», а столбцов 7. Кто должен отказать?

Агент написал функцию, тесты зелёные, но ревьюер не понимает код. Мержим?

Зачем каждому дополнительная роль?

Ответ 1
Валидация на сервере: столбец в диапазоне, ход игрока, игра не окончена. Клиентская проверка — только для удобства.
Ответ 2
Код, который никто не понимает, — долг. Попросите агента объяснить и упростить, допишите тест на непонятный случай.

Коммит — снимок с подписью

Терминал
$ git status
$ git add game/board.py tests/test_board.py
$ git commit -m "game: проверка победы по диагонали"
$ git log --oneline
a3f9c21 game: проверка победы по диагонали
7be4d02 game: поле 6×7 и ход в столбец
  • Коммит хранит всё состояние файлов, автора, время и сообщение.
  • Хороший коммит — одно логическое изменение.
Терминал
$ git status
$ git add game/board.py tests/test_board.py
$ git commit -m "game: проверка победы по диагонали"
$ git log --oneline
a3f9c21 game: проверка победы по диагонали
7be4d02 game: поле 6×7 и ход в столбец
Как устроено
Коммит — объект с хешем SHA-1 (в новых версиях есть SHA-256). Ссылается на дерево файлов и на родителя. История — цепочка родителей.
Индекс
git add кладёт изменения в индекс (staging area). Коммит записывает индекс, а не все изменения рабочей папки.

Pull request — предложение изменения

  • PR = «вот моя ветка, давайте вольём её в main».
  • В описании: что сделано, как проверить, ссылка на issue (Closes #12).
  • PR проверяют CI (тесты, линтер) и ревьюеры.
  • Merge — только после одобрения и зелёного CI.
Маленький PR проверят за 10 минут. PR на 2000 строк не проверит никто — его просто примут с ошибками.
Шаблон PR
«Что сделано», «Как проверить», «Скриншоты», «Что сгенерировал агент». Последний пункт обязателен в нашем проекте.
Стратегии слияния
Merge commit сохраняет историю ветки. Squash превращает PR в один коммит — у нас по умолчанию squash.

Ревью: что смотрим

Работает?
Есть ли тест? Проходит ли CI? Проверили ли руками?
Соответствует спеке?
Сверяем с критериями приёмки issue и SPEC.md.
Понятно?
Имена, длина функций, нет ли лишнего кода от агента.
Безопасно?
Нет секретов, проверены входные данные, нет доверия клиенту.
Ревью — не экзамен. Комментарий пишем про код, а не про человека: «здесь упадёт на пустом списке», а не «ты не подумал».
Ревью агентом
Агент-ревьюер быстро находит опечатки, пропущенные проверки, несоответствие стилю. Но не знает намерений: решение принимает человек.
Метрика
Считаем число итераций ревью на PR. Если у PR агента их больше 3 — проблема в спеке или в AGENTS.md.

conflict в game/board.py
<<<<<<< HEAD
ROWS, COLS = 6, 7
=======
ROWS, COLS = 7, 8
>>>>>>> feature/20-big-board

  • Оставить нужное, убрать маркеры, запустить тесты, закоммитить.
Чем меньше и короче ветки, тем реже конфликты. Регулярно подтягивайте main.
conflict в game/board.py
<<<<<<< HEAD
ROWS, COLS = 6, 7
=======
ROWS, COLS = 7, 8
>>>>>>> feature/20-big-board
Решение
git merge main в своей ветке → правка файлов → git add → git commit. Или git rebase main для линейной истории — только для своей, ещё не опубликованной ветки.

Демо: от issue до merge

  • Создаём issue «кнопка Играть» с критериями приёмки.
  • git switch -c feature/1-play-button, коммит, push.
  • Открываем PR с Closes #1, просим агента сделать ревью.
  • Человек сверяет замечания агента, одобряет, merge.
Смотрите на доску: задача сама переехала в Done, когда PR закрыл issue.
Что заметить
Ссылка Closes #1 закрывает issue при merge в ветку по умолчанию. Ветку после merge удаляем.
Если у вас Windows
Git Bash или WSL. Команды одинаковые. Проверьте git config --global core.autocrlf.
